# Architecture

## Product Boundary

Canonical founder policy (intentionally identical to the public README):

> Subagent007 is a universal execution-attempt substrate, not a workflow or mission owner. A run represents one concrete delegation attempt. Subagent007 guarantees exact admission, duplicate-safe identity, bounded execution, live observation and control, durable terminal evidence, and honest owner-loss closure. It does not guarantee that an active attempt survives loss of its execution custodian. Callers own durable objective identity, retry and reconciliation policy, and external-effect safety. Bendum therefore preserves and resumes the logical project obligation, reconnects to a still-owned attempt when possible, and creates a fresh fenced attempt only after the prior attempt is conclusively settled and replacement is canon-authorized.

The universal boundary ends before Bendum's composition sentence: Subagent007 owns concrete attempt admission, execution custody, observation/control, and terminal evidence. Callers own the higher-order obligation and decide whether settled evidence permits another attempt.

| Identity | Owner | Architectural meaning |
|---|---|---|
| caller objective/workflow step | caller | Durable logical obligation; deliberately absent from Subagent007 state. |
| `client_start_id` plus normalized request | caller chooses; Subagent007 binds | Exactly one admission identity. Exact replay joins the same run; changed reuse conflicts. |
| `run_id` | Subagent007 | Exactly one attempt record. It is never recycled into a replacement attempt. |
| `session_id` | Pi/Subagent007 internal continuity | Semantic context only; not run liveness, execution authority, or mission identity. |
| child process and server owner | current Subagent007 execution custodian | Live execution authority. Definite owner loss produces honest terminal `restart_drift`, never asserted reattachment. |

The base substrate is composable because it exposes universal attempt mechanics without importing caller semantics. A caller needing ambiguous-start protection persists `client_start_id` and the exact request before calling `start_run`; a caller needing logical retry persists its own objective and reconciliation state. A new persistent-custody capability is admissible only with a current universal sponsor and a real owner that can observe and enforce survival. A lifetime enum, Bendum-specific state, or another workflow control plane cannot manufacture that guarantee.

## System Overview
MCP client calls `dist/server.js` -> `src/server.ts` validates tool input and maps semantic rejections.
`run_subagent` is always a synchronous `quick_noninteractive` one-shot under its bounded internal deadline: it rejects caller `timeout_ms`, applies the one-shot health gate, and never classifies prompt text or redirects work to a durable async path. Callers explicitly select `start_run` or `schedule_run` for long, pollable, cancellable, or interactive work. Durable/session `timeout_ms` admission is mechanical and numeric only.
Run requests go through config/model/skill validation, then `src/runTask.ts` creates a durable run state keyed by `run_id`.
`src/activeChildLease.ts` atomically admits top-level durable runs either to an active-child lease or to a bounded metadata-only owner queue. One process-owned pump promotes that owner's in-memory requests in order, avoiding per-ticket filesystem polling. New lease paths bind run and owner identity; unreadable records conservatively retain capacity, while unreadable legacy owner-only records classify liveness as unknown rather than claiming a specific run. Confirmed lease deletion follows durable terminal publication; restart reconciliation recognizes live queue tickets and only attributable active leases.
`src/runSubagent.ts` writes a Pi child request file, then `src/processRunner.ts` spawns and supervises the child process with serialized output consumption and a protected-free-disk watermark. `src/runTask.ts` and `src/activeChildLease.ts` own finite local capacity.
For `effect_profile:"workspace_read_only"`, `src/piChild.ts` disables ambient extension discovery, explicitly binds `pi-search-hub`, passes the exact seven-tool allowlist to Pi at `createAgentSession`, excludes recursive control/delegate, verifies active tools, and emits a pre-prompt receipt. Neutral `task_root_authoring_v1` exposes only ordered `read`,`write`; creator-named `skill_creator_authoring_v1` retains its historical six-tool order. `src/authoringEffectScope.ts` owns the new scoped profiles' exact task-root identity, bounded initial-tree capture, sparse/multi-link rejection, separate writable closure limits, and terminal reinspection after every child outcome. Neutral writes target only canonical new `allowed_output_paths`, all required at closure with no extra entry. AJ direct and controller mutations target its fresh `.subagent007/assumption_audit_bounded_v1` root. Researcher controller state stays under its fresh `.subagent007/researcher_bounded_v1` root, but model-visible write/edit is confined to the exact real `input_root`; `job.json` and provider accounting remain controller/runtime-owned. Initial content outside either state root stays immutable and read-only controller arguments may reference it. Researcher activation receipt v4 advertises `researchctl_state_paths_v1` plus `researchctl_strict_v2`; `state-paths` returns exact bound job/input paths without state creation, while the shared serialized queue admits exact `init` only after canonical binding/argv/controller validation, establishes and captures the real state/input directory identities, and rechecks them immediately before execution and after success. Exit zero additionally requires canonical regular single-link `job.json`, exact input root, and writable closure; failure never causes provider retry, deletion, rollback, or synthetic success. `src/researchDispatchMediator.ts` intercepts top-level `web_search`/`web_read` and uses a non-registerable controller adapter to claim the sole tool+canonical-arguments reservation before provider execution and record the returned/error result afterward. Those private transitions and model-visible Researcher controller commands share one `BoundedControllerExecutionQueue`; the public tool schema and runtime allowlist exclude the two private dispatch commands. AJ retains bounded receipt v2 and its direct, unqueued controller path. `src/taskRootAuthoringTools.ts` enforces direct paths/payloads and `src/boundedController.ts` rechecks state after each call. At terminalization, strict Researcher success requires the exact snapshot script to validate one unchanged complete strict-dispatch job, render primary and Bendum packet projections, canonicalize both through the same control-free projection used by publication, and bind both hashes. `src/terminalProjection.ts` owns the single pure producer/durable structural join: non-Researcher projections forbid receipt/packet; exact legacy v3 durable projections allow one primary and at most the weaker exact v1 receipt; strict v4 completion requires the exact v2 receipt and one named primary+packet pair, while non-complete or activation-failure projections retain one diagnostic primary without receipt/packet. Failed, cancelled, and timed-out strict runs may retain a v2 pair only when materialization completed. Hashes join by role name, never list order. Generic process success remains transport-only, legacy v3 is never admitted at live ingress, and the validator does not prove controller execution ran. The fixed controller still binds and rechecks the exact snapshot script plus resolved Python identity/imports and never re-resolves `PATH`. This is a bounded Pi dispatch/path/controller/terminal observation claim, not filesystem atomicity, an OS sandbox, or hostile-native TOCTOU prevention. When `expected_skill_sha256` is present, the parent verifies the canonical skill before launch and places those bytes in the run-owned child-request directory; Pi expands the snapshot while the receipt identifies the canonical source.
`verify_skill_bindings` stays outside that execution graph. `src/server.ts` validates its strict version-1 canonical batch, then `src/skillVerification.ts` loads one catalog through `src/skillResources.ts` and applies the same skill-file read/hash/compare primitive used by launch. The handler returns an in-memory all-or-nothing point-in-time result and deliberately bypasses child readiness, model/config resolution, run/session registration, admission, snapshots, leases, events, temporary artifacts, caches, and failure logging.
`resolve_skill_bindings` shares that non-execution boundary and the same one-catalog/read/hash authority, but accepts hashless canonical names and returns their canonical paths and hashes in a full-request-bound all-or-nothing response.
`src/skillRuntimeBundle.ts` owns the complete admitted-runtime closure (including canonical root `license.txt`) and one domain-separated digest over canonical paths, executable bits, and exact bytes. `validate_skill_runtime_bundle` applies it to caller-selected staging or canonical source without catalog authority; `resolve_skill_runtime_bundles` applies it after one canonical catalog load. `src/skillSnapshotStore.ts` internally materializes that captured closure at a content-addressed owner path and retains exact project/publication references. Publication identity uses a Bendum-persisted `publication_id`, not the later manifest hash, so crash retry is non-circular and idempotent. Public `resolve_retained_skill_snapshot_source` accepts one exact retained identity, validates active/closed committed reference and immutable runtime bytes, and returns only the owner-controlled content-addressed runtime source identity. It takes no caller-selected filesystem path and performs no copy, staging, lock, or retained-state mutation; a consumer copies and revalidates under its own transaction. The former caller-path rollback staging operation is retired.
For `start_run`, `src/clientStartAdmission.ts` strictly schema-normalizes the request, excludes only `client_start_id`, canonicalizes object keys by code-point order, and atomically hard-links then fsyncs a unique key binding inside the existing run-task store before queue/child admission. Optional `system_skill_name` is part of that exact identity, so same-key governor drift conflicts before another run or child exists. Before the claim, `runTask.ts` writes only a private `.prepared` candidate in the same run-task directory; it is not addressable by `get_run` and carries non-admitted progress. Once the binding is authoritative, winner or replay atomically hard-links that exact candidate to the canonical run snapshot without polling. Losing/dead pre-binding candidates are removed, live replay stays prompt, and definite post-binding owner loss uses only the existing restart-drift terminalization path.
Every configured runtime persisted-run read accepts only the exact `subagent007.current_run_claim` representation; direct-v2, bare-v3, and historical `subagent007.run_owner_record` envelopes fail before liveness, reconciliation, control, or settlement and are not rewritten. The shared current-v3 snapshot validator derives owner-terminal lifecycle from existing fields rather than persisting another discriminator. Request declarations may exist before launch; once the prompt is submitted, triggered activation, snapshot, recursive-delegation, and effect-scope observations must pass their existing strict owner validators and join the request exactly. Child-process terminal readback also classifies the validated activation and calls the same pure terminal-projection validator used by the producer, so packet admission cannot bypass Researcher v4 plus an exact v2 receipt. Terminal owner state requires exactly one matching final settlement event. This lets a constrained cancellation before child launch persist without counterfeit child receipts while keeping post-child evidence fail-closed.
`src/runTask.ts` reuses the existing per-run owner as the only observable lifecycle-state writer. While a `RunTaskState` is resident it is the semantic working source; without one, the durable owner record is. Every claim-bearing producer submits a small named operation. Under the owner, the operation reads fresh durable truth, clones a private draft, applies its event-specific idempotency rule, constructs any canonical public event once, derives and validates the unchanged public durable-run v3 projection, atomically persists the next revision, and synchronously publishes that exact draft. Only after release does it append the byte-identical event as non-authoritative JSONL staging or perform mailbox, wait, logging, and cross-run work. Persisted reads never overlay JSONL or input staging. Stable beats, receipts, spawn, cancellation, settlement, and timeout enrichment may exact-no-op; repeated general output/session/lifecycle evidence remains observable, projection is monotone, and terminal state absorbs all later claims except the exact existing timeout-recovery hint enrichment. Terminal publication treats the caller-supplied later owner projection as authoritative, applies the child-evidence filter and existing 25-event bound directly, preserves multiplicity already present there, and retains up to two spawn anchors without merging an earlier projection.
Spawn is one such operation: admission records `queued_at`, Node's real spawn callback captures the start timestamp, and the owner atomically commits the exact `child_spawned` anchor, launch observation, `child_started_at`, arithmetic `queue_wait_ms`, and public projection. The existing stdin control pipe then receives one private release frame; consequential child work waits for it and EOF before release exits. This gate is the bounded repair justified by the producer-real SIGKILL characterization. JSONL append follows release from owner, and staging failure kills/terminalizes from complete owner truth. Terminal projection retains the anchor within its 25-event bound. Child lifecycle advances in producer order—spawn, bridge, recursive receipt, session, optional activation, optional snapshot, prompt—without requiring absent optional stages.
Restart descendant reconciliation is deliberately two-phase. It acquires/reads/releases the parent owner, recursively inspects descendants with no parent owner held, then reacquires and rereads the parent. It reassesses fresh parent identity/lifecycle/settlement and exact descendant membership/status obligations; a changed revision from compatible heartbeat/progress is not rejection. It commits from the fresh parent only when those semantic facts still authorize reconciliation, otherwise it retries through the existing bounded route. At most one run owner is held.
Snapshot launches never resolve mutable source. The parent validates owner metadata, complete bytes, active reference, and publication receipt before task registration and again at execution; `piChild.ts` repeats the validation immediately before prompt and emits the exact activation receipt. Active references transition idempotently to closed without changing reference/snapshot identity. Both lifecycles remain retained and included in deletion impact; deletion recomputes the full project/reference impact under the snapshot lock.
Child output is projected directly into a sanitized private-locator `.partial` transcript through `src/output.ts`; normal execution does not persist a private raw stdout/stderr spool. Terminal document bytes are capped at 1 MiB per file during final-message writes and backpressured transcript streaming. One no-follow descriptor finalizer captures exact regular single-link descriptor/path identity around the pre-rename hook, renames, captures post-rename `S0`, hashes exactly its bounded descriptor bytes with short-read rejection, requires exact regular single-link `S1`, verifies the final pathname names `S1`, and only then emits the required primary `{relative_path,size_bytes,content_sha256,...}` reference from `S1`. Strict Researcher prepares and hashes both role files first, persists one exact private pending pair under the durable run owner before the first public rename, and atomically drops that pending ownership only when terminal references own both paths. In-process failure deletes the pair; owner-loss reconciliation deletes any recorded staged or partially published pair before restart-drift settlement, and a failed cleanup remains durably owned for startup retry. Restart transcript recovery uses the same bounded post-rename/final-path inspection. These are point-in-time final-state witnesses; later mutation is caller-recaptured from the configured runs root rather than prevented by provider locking/copying/state. Public run projections expose neither internal pending ownership, the partial transcript locator, nor an absolute final path; callers derive canonical single-component basenames from the configured runs root. Final-only success removes the redundant transcript staging file. Sanitized public events flow through run-event helpers, and failure records through `src/failureLog.ts` without output paths. Requested `final` output normally succeeds only when the child writes a final message; strict Researcher instead requires controller-owned primary+packet render artifacts. Missing required artifacts are classified as `missing_final_output`, with transcript output retained as diagnostics.
Server-authored prompt provenance uses `src/prompt.ts` to project caller prompt text to a redacted public marker before it reaches public event views or transcript artifacts; child execution still receives the real composed prompt.
Opt-in `system_skill_name` resolves through `src/skillResources.ts`' canonical catalogue authority on every launch. In that mode `DefaultResourceLoader` receives the complete Subagent007 catalogue with only the governing entry filtered; any different selected-skill snapshot remains first for its ordinary specialist name. `src/systemSkill.ts` rereads the current governing source and supplies the last inline extension, which receives Pi's chained `before_agent_start` system prompt, removes duplicate exact governing bodies, appends one canonical source-identified body as the suffix, and emits a strict name/path/body-digest/final-prompt-digest/exactly-once receipt. Its observation ceiling is Pi's system prompt after `before_agent_start`, not later provider-payload rewriting, serialization, or model obedience. The mode creates no governing prompt snapshot, generated prompt copy, version ledger, session-manifest field, or workflow state; named sessions and effect profiles reject it.
Only explicitly recursion-enabled launches receive a private recursive control payload. `src/piChild.ts` emits a separate pre-prompt authorization receipt and exposes `delegate` only when enabled. Descendants inherit root recursive authority and any confirmed governing system-skill name through private server construction. A governed lineage also carries the root's resolved model class only in that authenticated private context: the child tool omits `model_class`, the server compares the context to the active parent and rejects any selector/forgery, then launches each descendant with the inherited class. Generic recursion retains its model selector. Because this child-facing caller has no `get_run`, `src/recursiveDelegateTool.ts` normalizes omitted `wait_ms` to a bounded 30000 ms request while preserving explicit zero/positive values; the public `schedule_run` default remains 1000 ms. This changes response timing only: the run owner remains `src/runTask.ts`, configured scheduler ceilings may truncate the wait, and a slower descendant may still return `working`. `src/runTask.ts` records complete ancestor descendant order/status and delays each parent terminal snapshot until its direct children have recursively settled.
`get_run`, `answer_run_input`, and `cancel_run` operate through that owner or observe its synchronously published committed resident state. `get_run` omission/zero preserves immediate snapshots. A positive bounded wait on a resident non-actionable run subscribes outside the owner lock to post-release committed-state publications and returns on `input_required`, terminal state, or one expiry timer; heartbeat/progress can wake the condition check without becoming a return state. The same publication wait replaces the scheduler's former short timer polling. A nonresident run has no owner-record event stream in the observing process, so `get_run` reads current persisted truth once and returns immediately rather than polling the filesystem or exposing a public revision. Every answer carries a response ID over the parent-owned child stdin control channel; mailbox registration precedes send, the child emits a correlated acceptance event only after its waiter takes the response, and the parent owner commits safe settlement before returning the receipt. Cancellation and terminalization first commit pending-request closure intent under the owner, then settle mailbox files outside it. Raw answers are never written to mailbox sidecars or public run surfaces.
The MCP response projection strips backend Pi session IDs and internal mailbox filesystem paths while internal snapshots retain the data needed for recovery; callers use run/request IDs and output references instead.
After an atomic terminal snapshot captures the bounded public event projection and settled input views, `runTask.ts` removes that run's redundant event ledger and mailbox directory. A task with an accepted caller input retains only its hashed response identity and receipt in the live server process so an exact retry can survive a fast terminal transition; it is not persisted, so process loss still fails closed. Other terminal task state evicts after confirmed capacity release. Active and input-required runs retain both. Snapshot temp files are removed on local failure; startup recovers a valid dead-owner temp only when no canonical successor exists, and otherwise removes only provably dead-owner temps. Named-session candidate directories remain isolated during execution, then `session.ts` removes the exact attempt workspace after canonical promotion or failure telemetry persistence; the recorded attempt session id is historical audit metadata rather than a durable path.
Operation-only semantic failures from those run-operation tools project as `kind:"operation_rejected"` instead of MCP text errors; child-invocation preflight failures remain `kind:"preflight_rejected"` with `child_started:false`.
The protocol-deterministic observed probe creates its fake Pi child under one exact temporary root and encloses initial client connection plus all scenario execution in the same cleanup ownership boundary. Optional client close and fake-root removal run in nested `finally` blocks, so initial connection failure preserves its original error while leaving no generated fake state.
Named sessions add `src/session.ts` manifest/ledger/lock handling around the same child execution path. Locks remain owned until matching release or definite local owner death. A hash-verified pending commit publishes the canonical session file, ledger record, and manifest in recoverable order; the retained candidate workspace is deleted only after all three are verified. Manifest eligibility failures known before launch, such as missing `require_existing` sessions, reject before durable task registration with `preflight_rejected` and `child_started:false`; locked execution checks still run later as race protection. Terminal session failures logged after durable task creation preserve the caller tool, durable `run_id`, and `task_kind:"session"` so telemetry can be correlated with public run views.

## Key Components
- `server.ts` - MCP tool surface, schema/preflight rejection shape, retry and cancellation-eligibility guidance, and failure logging for handler-level failures.
- `skillVerification.ts` - canonical batch request digest, read-only typed result projection, and the shared resolved-skill file read/hash/compare primitive used by verification and launch.
- `systemSkill.ts` - current-source governing-skill read, final inline Pi system-prompt composition, exactly-once suffix check, and strict narrow receipt validation.
- `skillRuntimeBundle.ts` / `skillRuntimeBundleValidation.ts` - canonical complete closure/digest and exact-root read-only public validation.
- `skillSnapshot.ts` / `skillSnapshotStore.ts` - public publication/lifecycle/activation contracts plus immutable materialization, references, locks, retention, and deletion impact.
- `runTask.ts` - one-shot and durable task lifecycle, snapshots, background execution, cancellation, caller input closure, and active-child lease release.
- `runClaimLock.ts` - temporary per-run cross-process critical section with name/version/pid/nonce owner identity, permissive historical extra-key decoding, and whole-byte release fencing.
- `runTask.ts` also records recursive lineage metadata: `parent_run_id` for descendants, `root_run_id`, `recursion_depth`, direct `child_run_ids`, and parent public events for recursive child start/finish.
- `runSubagent.ts` - child request-file contract, Pi child invocation, transcript/final-output handling, missing-final classification, timeout metadata, provider error parsing, recursive control payload injection, skill snapshots/audit metadata, and activation-receipt validation.
- `recursiveControl.ts` / `recursiveDelegateTool.ts` - private local IPC and child-facing `delegate` tool for recursive Subagent007 calls; the child tool is a client, not an owner of durable task state.
- `processRunner.ts` - detached child process execution, backpressured line delivery, timeout/cancel/disk-reserve termination, heartbeat notifications, parent-exit process-group cleanup, and the single owner-commit release frame. The Pi bridge waits for release before consequential work and treats control-channel EOF as parent loss.
- `failureStorage.ts` / `failureStorageWorker.ts` - one locked append/archive owner with an aggregate raw-byte budget, oldest-archive-first pruning, whole-record active-ledger compaction, and a bounded unref'ed worker that keeps telemetry off caller response latency.
- `diskReserve.ts` - preflight and active-run host free-space protection; it stops work rather than truncating a continuing transcript.
- `ownedTemporaryArtifact.ts` - owner metadata and startup reconciliation for child-request/final-message temp directories.
- `buildReleaseLease.ts` / `scripts/build-atomic.mjs` - versioned build publication through `dist/current`, live-release protection, and the lease-owned loaded-release identity that runtime readiness compares with the `dist/current` release before reporting ready.
- `session.ts` - named-session manifests, read-only preflight eligibility checks, non-expiring local session locks, hash-verified pending commits, candidate ledgers, packet policy, skill/cwd immutability, and session terminal failure telemetry with durable caller context. Required packet failures distinguish missing, malformed, and parse-valid not-ready packets by reason code.
- `runtimeReadiness.ts` - built-entrypoint, source-state, contract, and public-tool readiness checks.

## External Dependencies
- Pi agent/runtime - child execution backend; Pi auth and model config must be visible to the MCP server process.
- Model providers via Pi/OpenRouter/Ollama inventory probes - reconciled by scripts, but concrete model ids and thinking levels are internal calibration behind public model classes.
- `@modelcontextprotocol/sdk` - public server/client protocol for tool listing and tool calls.
- Local filesystem - durable run snapshots, failure logs, input mailbox, sessions, model health, and active-child leases live under the state root.
- Git/source tree - runtime readiness can fail closed on dirty, unknown, or stale built source state.

## What Does NOT Exist Here
- No caller mission, workflow-step ledger, canon state, retry/reconciliation policy, or external-effect authority.
- No guarantee that a live child survives loss of its execution custodian, and no cross-process live-child reattachment claim.
- No queue for one-shot, named-session, or recursive launches; only top-level `start_run` and `schedule_run` use bounded admission queueing.
- No database, remote worker service, or distributed lock manager; persistence and locks are local files.
- No public concrete model or thinking-level input, result field, failure-log field, session ledger field, or README calibration table; callers use model classes and class-level health/migration guidance.
- No ignored public tool selector. The opt-in `effect_profile:"workspace_read_only"` is the enforced Pi construction-time ceiling.
- No OS sandbox or hostile-runtime containment claim for effect profiles.
- No full recursive descendant tree manager or cascade cancellation; the first recursive slice is one child-facing delegate tool plus direct lineage metadata.
- No exposure of raw thinking, private tool payloads, caller prompt text, full composed prompts, or input answer values in public event views.
